# Optical Manager

Optical Manager هو نظام إدارة محلي لمحل البصريات والنظارات، مصمم لتبسيط إدارة العملاء، وصفات وقياسات النظر، الفواتير، المدفوعات، الديون، المصروفات، والإدارة المالية اليومية.

المشروع موجه حاليًا للاستخدام الفردي داخل محل واحد، مع إمكانية تشغيله كتطبيق Web أثناء التطوير، وتغليفه كتطبيق Windows Desktop باستخدام Electron للاستخدام النهائي.

---

## 📌 نبذة عن المشروع

تم تصميم Optical Manager ليكون نظامًا بسيطًا وسريعًا لمحل النظارات، بحيث تتم العملية الأساسية من مكان واحد:

1. إدخال بيانات العميل.
2. إدخال قياسات النظر.
3. إنشاء الفاتورة.
4. تحديد السعر والخصم.
5. تسجيل المبلغ المدفوع.
6. حساب المتبقي تلقائيًا.
7. حفظ البيانات في SQLite.
8. طباعة الفاتورة.
9. متابعة الديون والمدفوعات.
10. إدارة المصروفات والحركات المالية.
11. إغلاق الصندوق يوميًا.
12. استخراج كشف حساب العميل.
13. إنشاء واستعادة النسخ الاحتياطية.

### 💰 الحالات المالية للفواتير

الفاتورة يمكن أن تكون:

```
UNPAID
PARTIALLY_PAID
PAID
CANCELLED
```

ويتم حساب:

```
paid = مجموع الدفعات الفعلية
remaining = total - paid
```

ولا يعتمد النظام المالي على قيمة قديمة أو يدوية للمدفوع، بل يتم احتساب الرصيد اعتمادًا على الحركات المالية المسجلة.

### 🏦 إغلاق الصندوق

يدعم النظام إغلاق الصندوق حسب اليوم.

يتم احتساب:

```
الرصيد الافتتاحي + المبيعات + التحصيلات - المصروفات = الرصيد المتوقع
```

ثم يقوم المستخدم بإدخال:

```
الرصيد الفعلي
```

ويحسب النظام:

```
الفرق = الرصيد الفعلي - الرصيد المتوقع
```

حالات الإغلاق:

```
OPEN
CLOSED
```

بعد إغلاق اليوم تصبح العمليات المالية لذلك اليوم محمية من التعديل.

---

### 🔒 قواعد الأيام المغلقة

عند إغلاق يوم مالي:

- لا يمكن تعديل فاتورة ذلك اليوم.
- لا يمكن حذف فاتورة ذلك اليوم.
- لا يمكن تسجيل حركة مالية جديدة في ذلك اليوم.
- لا يمكن تعديل الإغلاق بعد إتمامه بالطريقة العادية.

لكن يمكن تسجيل دفعة لفاتورة قديمة في يوم جديد مفتوح.

مثال:

```
فاتورة: 2026-09-01
اليوم الحالي: 2026-09-10
يمكن تسجيل دفعة جديدة بتاريخ: 2026-09-10
```

وهذا يسمح بإدارة الديون القديمة دون تعديل اليوم المالي المغلق.

## 🔐 النظام المالي كمصدر للحقيقة

في النظام المالي الحديث:

```
financial_transactions
```

هي مصدر الحقيقة للمدفوعات.

وبالتالي:

```
Paid = SUM(active PAYMENT transactions)
```

و:

```
Remaining = Invoice Total - Paid
```

ثم يتم تحديث حالة الفاتورة وفقًا للرصيد.

هذا التصميم يمنع حدوث اختلاف بين قيمة المدفوع الظاهرة في الفاتورة والحركات المالية الفعلية.
